# llm_based 项目面试题 300 问 300 答

## 一、项目概览

1. 问：`llm_based` 这部分项目的核心目标是什么？  
   答：基于已有医疗知识图谱，用 LLM 做查询规划和答案生成，完成自然语言医疗问答。

2. 问：它和 `rule_based` 的核心区别是什么？  
   答：`rule_based` 依赖手写规则分类，`llm_based` 依赖实体链接加 LLM 生成结构化查询计划。

3. 问：`llm_based` 是否复用规则版的 `question_parser.py`？  
   答：不复用，它单独实现了一套链路。

4. 问：`llm_based` 和 `rule_based` 共享哪些资产？  
   答：共享 `dict/` 词典和 Neo4j 图谱数据。

5. 问：`llm_based` 的主流程是什么？  
   答：实体识别 -> 查询计划 -> Cypher 构造 -> 图谱查询 -> 答案生成。

6. 问：为什么这个流程要拆成多层？  
   答：便于约束、调试、替换和排障。

7. 问：这个项目里的 LLM 主要承担哪两项职责？  
   答：查询规划和自然语言答案生成。

8. 问：为什么 LLM 不直接生成最终 Cypher？  
   答：直接生成风险更大，难以校验，容易越权或输出非法查询。

9. 问：为什么要保留知识图谱作为事实源？  
   答：让回答落到结构化事实，减少模型幻觉。

10. 问：这个项目最重要的设计思想是什么？  
    答：让 LLM 负责“理解”和“表述”，让图谱和白名单负责“约束”和“执行”。

11. 问：项目的主要模块有哪些？  
    答：`config.py`、`schema.py`、`entity_linker.py`、`llm_client.py`、`intent_planner.py`、`cypher_builder.py`、`graph_client.py`、`answer_generator.py`、`chatbot_graph.py`。

12. 问：哪一个文件定义了图谱允许查询的边界？  
    答：`schema.py`。

13. 问：哪一个文件负责对接大模型接口？  
    答：`llm_client.py`。

14. 问：哪一个文件负责实体识别？  
    答：`entity_linker.py`。

15. 问：哪一个文件是主入口？  
    答：`chatbot_graph.py`。

16. 问：项目的输入是什么？  
    答：用户自然语言问题。

17. 问：项目的最终输出是什么？  
    答：基于当前知识图谱生成的自然语言回答。

18. 问：项目依赖的核心外部系统有哪些？  
    答：LLM 接口服务和 Neo4j 图数据库。

19. 问：为什么说这个项目是检索增强但不是典型向量检索方案？  
    答：因为它增强的是结构化知识图谱查询，而不是向量相似度检索。

20. 问：如果一句话概括项目架构，你会怎么说？  
    答：这是一个“词典实体约束 + LLM 结构化规划 + Neo4j 执行 + LLM 受限表达”的医疗知识图谱问答系统。

## 二、实体识别与词典设计

21. 问：为什么项目没有让 LLM 直接抽取实体？  
    答：因为实体必须与当前图谱可识别范围对齐，词典更可控。

22. 问：`EntityLinker` 的核心职责是什么？  
    答：从用户问题中识别词典实体，并返回实体名、类型和对应 label。

23. 问：项目中有哪些实体类型？  
    答：疾病、症状、药品、食物、检查、科室、药企。

24. 问：这些实体类型在哪里定义？  
    答：`schema.py` 里的 `ENTITY_LABELS`。

25. 问：为什么实体类型还要映射成 Neo4j label？  
    答：因为图数据库查询依赖 label。

26. 问：`dict/` 目录在这个链路中的作用是什么？  
    答：提供实体识别和后续实体合法性校验的数据基础。

27. 问：为什么词典文件名要和实体类型名保持一致？  
    答：便于自动加载并减少硬编码。

28. 问：`EntityLinker` 初始化时做了什么？  
    答：加载词典、构造实体类型映射、建立 Aho-Corasick 自动机。

29. 问：为什么使用 Aho-Corasick 自动机？  
    答：它适合大规模词典的多模式串匹配。

30. 问：如果直接遍历所有词典逐个 `in` 判断，会有什么问题？  
    答：词典大时性能差，复杂度高。

31. 问：`matched_words` 表示什么？  
    答：自动机在问题中命中的所有词。

32. 问：为什么还要做 `stop_words` 处理？  
    答：去掉被长词包含的短词，保留更具体匹配。

33. 问：举个长词覆盖短词的例子。  
    答：如果同时命中“感冒”和“流行性感冒”，通常优先保留“流行性感冒”。

34. 问：`linked_entities` 最终包含哪些字段？  
    答：`name`、`types`、`labels`。

35. 问：为什么一个词可能对应多个类型？  
    答：真实数据中可能存在同名多义实体。

36. 问：项目现在如何处理同名多类型实体？  
    答：先全部保留给后续计划器使用，未做更复杂消歧。

37. 问：`validate_entity()` 的核心目的是什么？  
    答：校验 LLM 计划中的实体确实存在于对应词典中。

38. 问：为什么生成计划后还要再做实体校验？  
    答：防止 LLM 凭空新增实体或改写实体。

39. 问：如果 `label` 不是已知标签，校验结果是什么？  
    答：直接判定非法。

40. 问：这一层主要防住了什么风险？  
    答：模型幻觉实体、越权查询和无效数据库访问。

41. 问：实体识别层可能有哪些误差来源？  
    答：词典不全、同义词缺失、分词歧义、口语表达和错别字。

42. 问：如果用户说“血压高”，词典里只有“高血压”，会怎样？  
    答：当前可能识别不到，需要扩充别名词典或增加同义归一层。

43. 问：项目当前是否支持实体别名归一？  
    答：从现有代码看，没有单独实现。

44. 问：如何改进实体识别的召回率？  
    答：增加别名库、错拼纠正、拼音映射、同义词归一或混合 LLM 召回。

45. 问：为什么改进召回率时仍不能放弃校验？  
    答：召回增强和执行安全不是一回事，后者必须保留。

46. 问：如果要支持模糊实体匹配，难点是什么？  
    答：召回上升的同时会增加误匹配和错误查询风险。

47. 问：词典机制最大的优点是什么？  
    答：稳定、可控、性能好、结果可解释。

48. 问：词典机制最大的局限是什么？  
    答：对开放表达和未知别名的泛化能力有限。

49. 问：从工程角度看，这种设计更偏保守还是激进？  
    答：明显偏保守，优先保证可控性。

50. 问：面试时如何总结实体层？  
    答：项目用词典和 Aho-Corasick 做强约束实体识别，再用 label 校验阻断 LLM 幻觉实体进入执行链路。

## 三、Schema 与白名单约束

51. 问：`schema.py` 在项目中的定位是什么？  
    答：它是 LLM 输出和图谱执行之间的契约层。

52. 问：`PROPERTY_QUERIES` 定义了什么？  
    答：允许查询的属性白名单及其元信息。

53. 问：当前哪些实体支持属性查询？  
    答：代码里主要是 `Disease` 节点。

54. 问：`RELATION_QUERIES` 定义了什么？  
    答：允许查询的关系白名单、起止 label 和中文名称。

55. 问：为什么关系要记录 `start_label` 和 `end_label`？  
    答：用于校验方向和构造 Cypher。

56. 问：`SUPPORTED_ACTIONS` 的作用是什么？  
    答：限定 LLM 只能输出 `query_property` 或 `query_relation` 两种动作。

57. 问：为什么只保留两种动作？  
    答：先把范围收窄，降低复杂度和失控风险。

58. 问：`schema_for_prompt()` 是做什么的？  
    答：把约束摘要交给 LLM，帮助模型按白名单规划。

59. 问：为什么 prompt 里也要放 schema，代码里也要校验 schema？  
    答：前者是软约束，后者是硬校验，必须双层控制。

60. 问：如果只靠 prompt 约束，不做代码校验，会有什么风险？  
    答：模型仍可能输出非法字段，最终导致错误查询甚至安全问题。

61. 问：为什么 property 中文名和 property 字段名要分开？  
    答：字段名用于执行，中文名用于展示。

62. 问：在属性查询里，`cause` 和“疾病病因”的关系是什么？  
    答：前者是内部字段标识，后者是对用户展示的中文名。

63. 问：白名单设计最核心的收益是什么？  
    答：把 LLM 的开放输出收束成系统可验证、可执行、可维护的有限集合。

64. 问：如果要新增“治疗费用”查询，先改哪里？  
    答：先改 `schema.py` 的属性白名单，再补后续相关逻辑。

65. 问：为什么说 `schema.py` 是扩展点？  
    答：因为新增能力多数先从这里声明，再让上下游支持。

66. 问：如果图谱结构变化但 schema 不改，会有什么后果？  
    答：系统仍按旧约束执行，可能查不到结果或出现错配。

67. 问：为什么 schema 要尽量和图谱实际结构保持同步？  
    答：不然规划层和执行层会脱节。

68. 问：如果要接入多图谱源，schema 层会变复杂吗？  
    答：会，因为需要描述更多实体、属性、关系和目标源。

69. 问：你会如何评价当前 schema 的复杂度？  
    答：比较轻量，适合教学和中小规模演示。

70. 问：面试时如何强调 schema 层的重要性？  
    答：它是控制 LLM 可执行边界的核心安全层，也是让自然语言理解转成稳定数据库查询的关键。

## 四、查询规划器 IntentPlanner

71. 问：`IntentPlanner` 的输入是什么？  
    答：用户问题和已识别实体列表。

72. 问：它的输出是什么？  
    答：一个结构化查询计划 `plan`。

73. 问：为什么没有实体时直接不调用 LLM？  
    答：因为没有约束时 LLM 最容易臆造查询目标。

74. 问：项目给 LLM 的 payload 包含哪三部分？  
    答：问题、已识别实体、schema 摘要。

75. 问：系统提示词要求模型做什么？  
    答：只输出 JSON 查询计划，不回答医学问题。

76. 问：为什么系统提示词里要给出 `query_property` 和 `query_relation` 示例？  
    答：帮助模型对齐输出结构，减少格式漂移。

77. 问：为什么要解释 `direction` 的语义？  
    答：因为关系既可能正向查，也可能反向查，模型容易混淆。

78. 问：如果模型无法判断，提示词要求输出什么？  
    答：输出空对象 `{}`。

79. 问：为什么设计成输出 `{}` 而不是自由文本？  
    答：便于程序统一判空和降级。

80. 问：`_normalize_plan()` 的作用是什么？  
    答：校验并规整 LLM 输出，防止非法 action、property、relation、direction 进入执行层。

81. 问：为什么 `plan` 不是字典就要拒绝？  
    答：因为链路只接受结构化对象，不接受任意文本。

82. 问：为什么 `action` 不在白名单就要拒绝？  
    答：避免模型创造系统不支持的新动作。

83. 问：为什么 `subject` 必须是字典且要有 `name`、`label`？  
    答：因为后续 Cypher 构造和实体校验都依赖这两个字段。

84. 问：属性查询分支重点校验什么？  
    答：`property` 是否属于 `PROPERTY_QUERIES` 白名单。

85. 问：关系查询分支重点校验什么？  
    答：`relation` 是否白名单、`direction` 是否合法。

86. 问：为什么 `direction` 只允许 `outgoing` 和 `incoming`？  
    答：简化模型输出空间和查询构造逻辑。

87. 问：当前 `IntentPlanner` 是否做复杂多跳规划？  
    答：没有，当前只支持单个属性或单条关系查询。

88. 问：为什么先做简单计划格式是合理的？  
    答：单跳场景最常见，也最适合先搭建稳定基线。

89. 问：`_fallback_plan()` 在什么场景触发？  
    答：LLM 不可用或输出非法时触发。

90. 问：fallback 里优先处理哪类实体？  
    答：先疾病，再症状。

91. 问：疾病的 fallback 策略是什么？  
    答：查 `desc` 简介。

92. 问：症状的 fallback 策略是什么？  
    答：按 `has_symptom` 关系反查疾病。

93. 问：为什么 fallback 策略设计得很弱？  
    答：目标是保底可调试，不是替代完整规划能力。

94. 问：这个模块最关键的工程价值是什么？  
    答：把开放自然语言约束成固定查询计划协议。

95. 问：如果面试官问“为什么不直接让模型回答”，你在这一层怎么回答？  
    答：因为先规划后执行可以让答案建立在图谱事实之上，而不是模型记忆之上。

96. 问：如果用户问题里有多个实体，当前规划器能处理复杂组合吗？  
    答：能把多实体传给模型，但执行层仍主要围绕单个 `subject` 单跳查询。

97. 问：这意味着什么局限？  
    答：复杂多实体比较、交集或因果推理当前不支持。

98. 问：如果要支持“板蓝根颗粒能不能治疗感冒”这类双实体关系判断，现状够吗？  
    答：能部分覆盖，但不够系统，后续需扩展计划协议。

99. 问：为什么 `IntentPlanner` 适合独立成模块？  
    答：因为它是 LLM 推理边界和业务执行边界的分水岭。

100. 问：面试时如何总结规划层？  
     答：规划层是项目最关键的中枢，它用 prompt 和白名单把 LLM 的自然语言理解转换成系统可校验的查询协议。

## 五、LLMClient 设计

101. 问：`LLMClient` 的职责是什么？  
     答：封装 OpenAI 兼容聊天接口调用。

102. 问：项目为什么采用 OpenAI-compatible 接口设计？  
     答：便于切换不同兼容模型供应商。

103. 问：当前示例里默认连接的是哪类服务？  
     答：兼容模式的大模型服务。

104. 问：`chat_json()` 和 `chat_text()` 分别负责什么？  
     答：前者要结构化 JSON，后者要自然语言文本。

105. 问：为什么两种调用要拆开？  
     答：因为输出约束、温度和解析逻辑不同。

106. 问：`chat_json()` 为什么设置 `response_format`？  
     答：显式要求模型返回 JSON 对象格式。

107. 问：为什么 `chat_json()` 温度是 0？  
     答：希望结构输出稳定、可重复。

108. 问：为什么 `chat_text()` 温度不是 0？  
     答：回答生成允许适度自然化和润色。

109. 问：为什么无 API Key 时 `chat_json()` 返回 `{}`？  
     答：让上游可以自然走 fallback。

110. 问：为什么无 API Key 时 `chat_text()` 返回空字符串？  
     答：让答案生成层回退到模板回答。

111. 问：为什么 `_post_chat()` 要统一处理请求和返回解析？  
     答：集中复用网络逻辑，减少重复代码。

112. 问：为什么 `_post_chat()` 先从 `choices[0].message.content` 取内容？  
     答：因为兼容聊天接口的主要结果就放在这个位置。

113. 问：为什么 JSON 模式下还要再 `json.loads(content)`？  
     答：因为 `content` 本身仍然是字符串。

114. 问：如果模型返回了非 JSON 文本，结果会怎样？  
     答：解析失败并返回空对象。

115. 问：为什么这个返回空对象的策略有利于主流程？  
     答：主流程可以统一判空并降级。

116. 问：`_send_with_retries()` 做了什么？  
     答：对网络层可恢复异常做有限重试。

117. 问：哪些异常被视为可重试？  
     答：`URLError`、超时、连接错误、HTTP 通信异常、JSON 解析异常等。

118. 问：为什么 `HTTPError` 默认不重试？  
     答：因为多数 HTTP 业务错误是确定性失败。

119. 问：为什么要截取错误明细前 500 字符？  
     答：避免日志过长，同时保留足够排障信息。

120. 问：`last_error` 的作用是什么？  
     答：保存最近一次失败原因，供主流程调试输出。

121. 问：为什么客户端类里实现了 `_safe_payload()`？  
     答：为了打印调试日志时避免内容过长或泄露过多上下文。

122. 问：为什么 `_shorten()` 要限制长度？  
     答：长 prompt 直接全打印会淹没有效信息。

123. 问：为什么网络层要设置超时？  
     答：避免主流程无限阻塞。

124. 问：重试次数配置放在哪？  
     答：`config.py`。

125. 问：这个客户端的优点是什么？  
     答：无额外依赖、结构简单、便于替换供应商、具备基本重试和调试能力。

126. 问：它的不足是什么？  
     答：日志体系较原始、没有指数退避、没有更细粒度状态码策略。

127. 问：如果要提升生产可用性，客户端层还可加什么？  
     答：熔断、退避、请求 ID、限流、监控指标和敏感信息脱敏。

128. 问：为什么说这里的设计偏教学友好？  
     答：因为用标准库实现，逻辑透明，便于逐步阅读。

129. 问：如果改用 `requests` 或 `httpx` 会带来什么？  
     答：代码可能更简洁，也更适合异步和高级特性，但会增加依赖。

130. 问：面试时如何评价 `LLMClient`？  
     答：它是一个最小可用的兼容接口适配层，重点在稳定接入、有限重试和调试可观测性。

## 六、CypherBuilder 与查询执行

131. 问：为什么要单独有 `CypherBuilder`？  
     答：把计划解释和数据库执行分离。

132. 问：`build()` 方法根据什么分流？  
     答：根据 `plan["action"]`。

133. 问：属性查询构造的核心逻辑是什么？  
     答：按 `subject` 的 label 和属性白名单生成参数化 Cypher。

134. 问：为什么属性查询前还要判断 `subject["label"]` 是否匹配属性 schema？  
     答：防止把疾病属性查到其他实体上。

135. 问：这里的 `field` 为什么返回中文属性名？  
     答：便于后续模板回答直接展示。

136. 问：关系查询为什么分 `outgoing` 和 `incoming` 两种模板？  
     答：因为 subject 可能是关系起点，也可能是终点。

137. 问：正向关系查询的典型例子是什么？  
     答：疾病 -> 忌食 -> 食物。

138. 问：反向关系查询的典型例子是什么？  
     答：症状 -> 反查具有该症状的疾病。

139. 问：为什么 Cypher 里 label 和 relation 名可直接拼接？  
     答：因为它们来自内部白名单，不是用户自由输入。

140. 问：为什么 `subject_name` 必须参数化？  
     答：它来自用户问题映射结果，必须降低注入风险。

141. 问：这个模块在安全层面最重要的贡献是什么？  
     答：把自由文本执行风险压缩为白名单模板加参数化查询。

142. 问：`GraphClient` 的职责是什么？  
     答：连接 Neo4j 并执行参数化 Cypher。

143. 问：为什么 `GraphClient` 保持非常薄？  
     答：查询语义已经在上层决定，这里只做执行。

144. 问：当前连接 Neo4j 的方式是什么？  
     答：使用 `py2neo.Graph` 连接本地 bolt 地址。

145. 问：为什么说 Neo4j 连接配置目前偏硬编码？  
     答：地址、用户名、密码直接写在代码里。

146. 问：这会带来什么问题？  
     答：环境切换困难，也有安全风险。

147. 问：更合理的做法是什么？  
     答：把图数据库连接也放进配置或环境变量。

148. 问：`run()` 为什么对空 Cypher 直接返回空列表？  
     答：避免执行无意义查询，并保持返回结构统一。

149. 问：数据库结果用 `.data()` 返回后是什么形式？  
     答：列表，每一项是一个字典。

150. 问：为什么这种结果形式适合传给答案生成器？  
     答：结构简单，字段可直接按 key 访问。

151. 问：`CypherBuilder` 和 `GraphClient` 之间的接口是什么？  
     答：`cypher` 字符串和 `parameters` 字典。

152. 问：这个接口为什么比较清晰？  
     答：一边只负责构造，一边只负责执行，边界明确。

153. 问：如果查不到图谱结果，通常说明什么？  
     答：可能是图谱本身没有数据，或者计划方向/实体不匹配。

154. 问：如果用户问“鹅肉对什么病有好处”，这属于哪类查询？  
     答：关系反向查询，食物反查疾病。

155. 问：为什么关系反查能力很重要？  
     答：用户问题经常从目标节点发问，而不是从疾病发问。

156. 问：当前执行层支持多跳查询吗？  
     答：不支持，都是单跳模式。

157. 问：如果要支持“某症状常用什么药”，难点在哪里？  
     答：需要从症状反查疾病，再从疾病查药品，属于多跳。

158. 问：扩展多跳查询，哪一层最先要变？  
     答：计划协议和 `CypherBuilder`。

159. 问：为什么这个项目的 CypherBuilder 比规则版更灵活？  
     答：它不依赖固定问题类别，而依赖结构化计划。

160. 问：面试时如何评价执行层？  
     答：它通过白名单模板和参数化查询把 LLM 规划安全地落到 Neo4j 上，设计简洁但边界明确。

## 七、答案生成器设计

161. 问：`AnswerGenerator` 的职责是什么？  
     答：把图谱结果转成用户可读回答。

162. 问：为什么图谱没有结果时直接返回固定文案？  
     答：避免 LLM 在无事实基础时乱答。

163. 问：答案生成时传给 LLM 的内容包括什么？  
     答：原始问题、查询计划、图谱结果。

164. 问：为什么传查询计划给 LLM？  
     答：帮助模型理解这批结果代表什么语义。

165. 问：为什么 `graph_results` 要裁剪到 `num_limit`？  
     答：避免上下文过长和回答发散。

166. 问：系统提示词对回答生成器提出了哪些限制？  
     答：只能基于图谱结果回答，不能补充图谱外医学知识，不能给诊断结论，回答要简洁自然。

167. 问：为什么在医疗场景里强调“不能替代医生建议”？  
     答：降低误导风险，明确系统边界。

168. 问：为什么 LLM 回答生成失败后还要有本地模板？  
     答：让系统在无模型或模型失败时仍能产出可用结果。

169. 问：模板回答如何区分属性查询和关系查询？  
     答：根据 `plan["action"]` 分支。

170. 问：属性查询模板为什么从 `value` 字段取数据？  
     答：因为 Cypher 已统一返回 `value`。

171. 问：关系查询模板为什么从 `object` 字段取数据？  
     答：因为目标节点统一放在 `object` 字段。

172. 问：为什么 `_stringify()` 要处理列表值？  
     答：因为某些图谱属性是列表，如治疗方式。

173. 问：为什么 `_unique_non_empty()` 既要去重又要保序？  
     答：回答稳定且不重复，更利于用户阅读。

174. 问：为什么模板回答里会用“包括”这样的措辞？  
     答：说明结果可能不是穷尽，只是当前图谱中的部分命中。

175. 问：答案生成这一层最重要的安全措施是什么？  
     答：限制模型只能依据 `graph_results` 回答。

176. 问：如果模型仍然补充图谱外知识，怎么办？  
     答：可加强 prompt、加入输出审查，或更多依赖模板回答。

177. 问：为什么说这层是“自然语言润色层”，不是“事实决定层”？  
     答：事实已经由图谱查询确定，这里只是把事实说得更自然。

178. 问：项目当前是否支持答案引用来源字段？  
     答：没有显式来源展示，只强调来自当前知识图谱。

179. 问：如果要提升可解释性，答案层可以怎么改？  
     答：展示命中的实体、关系名、属性名或结构化证据片段。

180. 问：面试时如何总结答案层？  
     答：它采用“LLM 优先、模板兜底”的双轨设计，在尽量自然的同时把事实边界锁死在图谱结果内。

## 八、主流程编排 chatbot_graph

181. 问：`LLMChatBotGraph` 是做什么的？  
     答：串起整个 LLM 问答链路。

182. 问：主类里初始化了哪些核心组件？  
     答：`LLMClient`、`EntityLinker`、`IntentPlanner`、`CypherBuilder`、`AnswerGenerator`，以及懒加载的 `GraphClient`。

183. 问：为什么 `GraphClient` 不是直接初始化？  
     答：为了懒加载，降低调试前半段逻辑时对数据库环境的依赖。

184. 问：`chat_main()` 的默认回答是什么？  
     答：`当前知识图谱中没有查到相关信息。`

185. 问：为什么主流程里多次使用早返回？  
     答：让失败边界清晰，避免嵌套过深。

186. 问：第一步做什么？  
     答：实体识别。

187. 问：识别不到实体时为什么直接返回默认答案？  
     答：因为后续没有稳定的图谱约束基础。

188. 问：第二步做什么？  
     答：调用规划器生成结构化查询计划。

189. 问：计划为空时为什么直接返回？  
     答：说明无法形成合法查询。

190. 问：第三步为什么还要做实体校验？  
     答：阻断 LLM 篡改实体。

191. 问：第四步做什么？  
     答：把计划转成 Cypher 和参数。

192. 问：第五步做什么？  
     答：执行 Neo4j 查询。

193. 问：第六步做什么？  
     答：根据图谱结果生成最终回答。

194. 问：为什么 `chat_main()` 最后会打印 `llm_last_error`？  
     答：便于观察模型调用失败，但又不影响最终答案兜底。

195. 问：这个主流程最大的优点是什么？  
     答：每一步职责清晰且都可单独调试。

196. 问：这个主流程最大的限制是什么？  
     答：当前只支持简单单跳查询，不支持复杂推理。

197. 问：为什么 `run_debug_questions()` 很有价值？  
     答：它提供了一组覆盖主要场景的固定回归问题。

198. 问：这些调试问题覆盖了哪些分支？  
     答：属性查询、关系正查、关系反查、多实体和兜底场景。

199. 问：为什么教学型项目喜欢把调试样例写在代码里？  
     答：方便快速复现实验和讲解。

200. 问：面试时如何总结主流程？  
     答：它采用链式编排，把自然语言问答拆成六步，每一步都能独立约束和降级。

## 九、配置、启动与运行方式

201. 问：LLM 配置放在哪个文件？  
     答：`llm_based/config.py`。

202. 问：里面有哪些关键配置项？  
     答：API Key、Base URL、模型名、超时、最大重试次数。

203. 问：为什么 Base URL 使用 `.rstrip("/")`？  
     答：避免拼接接口路径时出现双斜杠。

204. 问：项目如何启动 LLM 通道？  
     答：在根目录执行 `python -m llm_based.chatbot_graph`。

205. 问：为什么推荐 `-m` 方式启动？  
     答：包导入语义更稳定。

206. 问：代码里为什么又兼容了直接执行文件？  
     答：降低使用门槛，便于本地单文件调试。

207. 问：如果没有配置 API Key，系统还能运行吗？  
     答：可以运行，但会退化为最弱兜底计划和模板答案链路。

208. 问：这种可运行但能力降级的设计有什么好处？  
     答：利于教学、调试和无外部依赖下的代码验证。

209. 问：为什么这是比“直接报错退出”更好的开发体验？  
     答：因为能先验证本地链路结构是否通顺。

210. 问：当前图数据库连接配置是否也应该抽到配置文件里？  
     答：应该，现状还有改进空间。

211. 问：如果部署到不同环境，哪些配置最需要抽离？  
     答：LLM 接口、数据库地址、账号密码、日志级别和超时策略。

212. 问：为什么说当前 `config.py` 更像演示配置？  
     答：因为其中包含敏感信息和固定值，不适合直接用于正式生产。

213. 问：生产环境更推荐什么配置方式？  
     答：环境变量或专用配置管理系统。

214. 问：项目支持替换别的 OpenAI 兼容模型吗？  
     答：支持，改 `LLM_BASE_URL` 和 `LLM_MODEL` 即可。

215. 问：这种兼容接口设计的工程价值是什么？  
     答：降低模型供应商切换成本。

216. 问：面试时怎么讲这一部分？  
     答：项目把模型接入做成兼容接口，运行时允许缺省降级，但数据库配置还需进一步工程化。

## 十、安全性与可控性

217. 问：这个项目最主要的安全风险点有哪些？  
     答：LLM 幻觉、非法查询、Cypher 注入、敏感配置泄露、医疗误导回答。

218. 问：项目如何防止 LLM 虚构实体？  
     答：只允许使用已识别实体，并在计划后再次做实体词典校验。

219. 问：项目如何防止 LLM 发明新关系或新属性？  
     答：通过 schema 白名单和 `_normalize_plan()` 双重限制。

220. 问：项目如何降低 Cypher 注入风险？  
     答：用户相关值用参数化传递，不直接拼接。

221. 问：为什么 label 和 relation 拼接进语句仍相对安全？  
     答：因为它们不是用户输入，而是来自内部白名单。

222. 问：项目如何防止模型在无查询结果时乱答？  
     答：图谱无结果直接返回固定文案，不调用 LLM。

223. 问：项目如何约束模型不要给诊断？  
     答：在答案生成 prompt 中明确禁止。

224. 问：为什么医疗场景下这种限制比普通问答更重要？  
     答：因为错误回答可能带来现实误导和风险。

225. 问：当前配置文件中最大的安全问题是什么？  
     答：敏感 API Key 明文写在代码里。

226. 问：如果面试官问“你会优先改哪项安全问题”，你怎么答？  
     答：先移除仓库中的明文密钥和数据库硬编码凭据。

227. 问：日志打印方面有什么隐患？  
     答：可能泄露过长 prompt、隐私问题或错误上下文。

228. 问：为什么要对日志做截断和脱敏？  
     答：既保留排障信息，又控制泄露风险。

229. 问：如果要进一步加强执行安全，还能做什么？  
     答：限制查询耗时、限制返回条数、只读数据库账号、增加结果过滤。

230. 问：为什么白名单比让模型“自觉遵守规则”更可靠？  
     答：因为白名单是代码硬边界，不依赖模型自律。

231. 问：项目是否完全避免了幻觉？  
     答：没有完全避免，但把幻觉影响压缩在较小范围内。

232. 问：幻觉主要还可能出现在哪一层？  
     答：答案生成层的自然语言润色阶段。

233. 问：为什么这个项目比纯聊天式医疗问答更安全？  
     答：因为事实必须先落到知识图谱命中结果上。

234. 问：如果要做更严格合规，你会怎么改回答生成器？  
     答：对高风险问题直接模板化，不再调用 LLM 自然语言生成。

235. 问：面试时如何总结安全设计？  
     答：项目不是相信 LLM，而是用词典、schema、参数化和图谱结果一步步夹住 LLM 的输出空间。

## 十一、容错、降级与稳定性

236. 问：这个项目有哪些主要失败点？  
     答：实体识别失败、模型请求失败、计划非法、数据库不可用、图谱无结果。

237. 问：识别不到实体时系统如何处理？  
     答：直接返回默认兜底答案。

238. 问：LLM 不可用时系统如何处理？  
     答：规划层走 fallback，答案层走模板兜底。

239. 问：为什么这种双层降级很有价值？  
     答：它让项目在失去模型能力时仍能保持基本可运行。

240. 问：网络异常为什么允许有限重试？  
     答：因为抖动、EOF、超时有一定概率可恢复。

241. 问：为什么重试次数不宜过大？  
     答：会放大延迟并可能加剧服务端压力。

242. 问：图数据库目前是否有重试机制？  
     答：从现有代码看，没有额外重试封装。

243. 问：为什么图数据库查询失败也值得单独处理？  
     答：它是事实源，一旦不可用整条链路就无法完成事实检索。

244. 问：项目里哪些地方体现了“默认保守失败”？  
     答：无实体不查、无结果不让模型发挥、非法计划直接拒绝。

245. 问：这种保守失败策略的好处是什么？  
     答：错答会减少，但可能牺牲一部分召回。

246. 问：为什么在医疗场景下更愿意接受“少答”而不是“乱答”？  
     答：因为错误医疗信息成本更高。

247. 问：如果数据库连不上，当前主流程会怎样？  
     答：大概率在执行阶段抛错，现有代码没有更细的数据库异常兜底。

248. 问：这是当前稳定性上的一个什么问题？  
     答：数据库异常处理还不完整。

249. 问：如何改进这部分？  
     答：给 `GraphClient` 增加异常捕获、超时、连接检测和友好错误返回。

250. 问：为什么说 fallback 不等于完整可用？  
     答：它只是最低保底，不代表系统功能覆盖充分。

251. 问：当前 fallback 最适合什么用途？  
     答：教学演示、局部调试和无 Key 情况下的链路验证。

252. 问：项目是否有熔断、限流、缓存？  
     答：从现有代码看，没有。

253. 问：如果线上化，这些能力是否重要？  
     答：很重要，尤其是 LLM 和数据库都属于高价值外部依赖。

254. 问：为什么答案层模板兜底是一个很好的工程细节？  
     答：因为即使模型回答失败，用户也不会完全拿不到结果。

255. 问：面试时如何总结稳定性设计？  
     答：项目对 LLM 有基本重试和两层降级，但数据库异常治理和生产级弹性能力还有提升空间。

## 十二、性能与扩展性

256. 问：当前链路最可能的性能瓶颈在哪里？  
     答：LLM 请求和数据库查询。

257. 问：实体识别层的性能表现为什么通常较好？  
     答：词典预加载加 Aho-Corasick 适合高效匹配。

258. 问：为什么说 `EntityLinker` 是以空间换时间？  
     答：初始化时加载词典和建自动机，换取查询时的高效匹配。

259. 问：为什么 `num_limit` 对性能有帮助？  
     答：减少传给 LLM 的结果长度，控制请求体和生成耗时。

260. 问：如果问题量很大，当前同步实现的限制是什么？  
     答：吞吐有限，请求会串行阻塞。

261. 问：要提升并发能力，哪一层最适合先改？  
     答：LLM 请求和 Web 接入层。

262. 问：为什么当前没有缓存？  
     答：项目更偏教学最小实现，还没有引入复杂状态管理。

263. 问：哪些内容适合缓存？  
     答：高频问题的计划结果、答案结果、图谱查询结果甚至实体识别结果。

264. 问：缓存最难的地方是什么？  
     答：命中粒度、失效策略和上下文差异。

265. 问：为什么图谱查询结果有时也适合缓存？  
     答：图谱更新频率通常低于查询频率。

266. 问：如果要支持更多查询类型，首先会增加哪里复杂度？  
     答：schema、计划协议和 Cypher 构造器。

267. 问：为什么单跳查询扩到多跳查询会明显变复杂？  
     答：需要表达中间节点、路径约束、聚合和多实体关系。

268. 问：如何让规划器更容易扩展？  
     答：把 plan 定义成更明确的结构化协议，而不是继续堆自由字段。

269. 问：为什么当前模块拆分对扩展有帮助？  
     答：每层都能单独替换或增强，而不需要重写整条链路。

270. 问：面试时如何总结性能与扩展性？  
     答：当前版本在实体识别上很轻快，但整体吞吐受限于同步 LLM 和单跳查询设计，适合作为可扩展基线。

## 十三、与 rule_based 的对比

271. 问：规则版最强的优势是什么？  
     答：稳定、可控、可解释、行为确定。

272. 问：LLM 版最强的优势是什么？  
     答：对自然语言表达更灵活，适应复杂问法更强。

273. 问：规则版最明显的缺点是什么？  
     答：规则覆盖成本高，表达稍复杂就容易掉线。

274. 问：LLM 版最明显的缺点是什么？  
     答：存在随机性、外部依赖和幻觉治理成本。

275. 问：为什么这个项目没有完全抛弃规则思想？  
     答：实体识别和查询边界仍然大量依赖规则和白名单。

276. 问：从架构上看，这个 LLM 版更像“全新系统”还是“规则系统升级版”？  
     答：更像在规则系统事实底座上增加 LLM 规划与表达能力的升级版。

277. 问：为什么说这不是“让模型包办一切”？  
     答：因为图谱、词典、schema、Cypher 执行都仍由程序控制。

278. 问：面试官如果问“什么时候你会优先用 rule_based”，怎么答？  
     答：需求稳定、场景固定、合规要求高时，我会优先规则版。

279. 问：什么时候更适合用 `llm_based`？  
     答：用户表达多样、问题形式不固定、需要更强语言理解时。

280. 问：最合理的生产思路可能是什么？  
     答：规则和 LLM 混合，规则负责高确定性场景，LLM 负责长尾表达。

## 十四、改进方向

281. 问：如果让你继续演进这个项目，你第一优先级会改什么？  
     答：移除明文密钥和硬编码数据库凭据，先补安全底线。

282. 问：第二优先级会改什么？  
     答：增强数据库异常处理和日志体系。

283. 问：第三优先级会改什么？  
     答：把 plan 结构做强类型约束，并补单元测试。

284. 问：如何提升实体识别召回？  
     答：增加别名词典、同义词归一、拼写纠错和候选召回机制。

285. 问：如何提升查询能力覆盖？  
     答：支持多跳、多实体比较、聚合统计和关系判断类计划。

286. 问：如何降低答案层幻觉？  
     答：更多模板化、结构化证据展示和输出审查。

287. 问：如何提高性能？  
     答：缓存、异步化、批量请求和更细粒度超时控制。

288. 问：如何提高可测试性？  
     答：依赖注入、类型提示、Mock 外部服务、拆分纯函数。

289. 问：如何提高可观测性？  
     答：引入结构化日志、链路 ID、指标监控和失败分类统计。

290. 问：如何让这个项目更适合线上服务化？  
     答：封装 API 层、配置中心、监控告警、鉴权和限流。

291. 问：如果要支持 Web 前端联动，后端接口层应返回什么？  
     答：建议同时返回回答文本、计划、命中实体和图谱结果摘要，便于调试和解释。

292. 问：如果要做多轮对话，这套结构还够吗？  
     答：需要补上下文记忆和指代消解，目前只适合单轮问答。

293. 问：如果要支持向量检索结合图谱，应该加在哪？  
     答：可加在实体召回前后，或作为图谱无命中时的补充检索通道。

294. 问：如果要支持英文或多语言，首先要改什么？  
     答：词典、prompt、数据源和图谱实体别名体系。

295. 问：如果要支持医生端专业问答，哪些地方要加强？  
     答：图谱质量、术语覆盖、证据展示和权限分层。

## 十五、面试收口题

296. 问：如果面试官问“这个项目最大的亮点是什么”，你怎么答？  
     答：亮点在于没有把 LLM 当成黑盒回答器，而是让它嵌在一个可校验、可执行、可降级的图谱问答链路里。

297. 问：如果面试官问“这个项目最真实的短板是什么”，你怎么答？  
     答：短板是查询能力目前仍偏单跳、数据库配置硬编码、生产级监控和异常治理还不够完整。

298. 问：如果面试官问“你在这个项目里最能体现工程意识的点是什么”，你怎么答？  
     答：我会强调白名单 schema、参数化 Cypher、实体校验、有限重试、模板兜底和懒加载这些设计。

299. 问：如果面试官问“这套方案为什么适合做课程讲解”，你怎么答？  
     答：因为模块边界清晰，链路短，既有 LLM 能力又保留了足够多可解释的工程结构。

300. 问：如果面试官让你用一分钟介绍 `llm_based`，你怎么答？  
     答：这是一个医疗知识图谱问答模块，先用词典识别实体，再让 LLM 在 schema 白名单内生成查询计划，随后把计划转成参数化 Cypher 查询 Neo4j，最后基于图谱结果生成回答；它的重点不是让模型自由回答，而是把模型能力限制在可控边界内。
